# Навчальний інцидент — інструкція ведучого

Розділ 8.3 лабораторної, контрольна точка КТ-5, задача BOOK-43.
Ведучий ламає сервіс, черговий шукає причину й відновлює роботу за
[`incident-drill-responder.md`](incident-drill-responder.md). Черговий
не читає цей файл до кінця навчань.

Це інструкція навчань 16.11.2026 (звіт —
[`incident-drill-2026-11-16.md`](incident-drill-2026-11-16.md)). Під час
них grep чергового по `docs/` знайшов цей файл, тому інструкцію для
наступних навчань ведучий тримає поза репозиторієм до розбору
(BOOK-49, див. runbook → Incident drill quick reference).

Сценарій: недоступна база даних (контейнер Postgres зупинено).
Обмеження за часом — 30 хвилин.

## 1. Підготовка

```bash
docker compose up -d db
npm run db:deploy && npm run db:seed
npm run build
mkdir -p .next/standalone/.next && cp -r .next/static .next/standalone/.next/
node .next/standalone/server.js 2>&1 | tee drill-server.log    # окремий термінал, залишити працювати
```

1. Відкрити http://localhost:3000 і створити 3–4 бронювання від різних
   користувачів (одне — на Grand Conference Hall, підтвердити його в
   `/admin`), щоб у базі були дані.
2. Зафіксувати стан даних: `npm run data:check > drill-before.txt`.
3. Перевірити, що сервіс працює:
   `BASE_URL=http://localhost:3000 bash scripts/smoke.sh` → `SMOKE OK`.

Файли `drill-*.log` і `drill-*.txt` у git не потрапляють (`.gitignore`).

## 2. Як зламати

```bash
scripts/break-db.sh        # зупиняє контейнер бази: docker compose stop db
```

Записати точний час — це **початок впливу**. Спробувати забронювати
аудиторію в інтерфейсі, щоб у лозі з'явилися помилки. Далі черговий
працює сам; ведучий лише записує хронологію і нічого не підказує
(якщо черговий застряг понад 10 хвилин — можна сказати «подивись
runbook»).

## 3. Як полагодити (еталонне рішення для звірки)

Що мав би знайти й зробити черговий:

1. **Симптоми:** `GET /api/health` → 503 `{"database":"down"}`;
   інші запити → 503 `{"error":"Database unavailable","requestId":…}`
   (BOOK-44); в інтерфейсі «Technical failure» (HTTP 503) з request id;
   у `drill-server.log` рядок операції з цим `requestId` містить
   `"errorCode":"ECONNREFUSED"` (BOOK-45);
   `npm run ops:report -- drill-server.log` → `ALERT`.
2. **Причина:** контейнер `booking-db` зупинено (`docker ps -a` →
   `Exited`); процес застосунку при цьому живий.
3. **Відновлення:** `docker compose start db`, дочекатися healthy.
4. **Перевірка:**
   - `curl http://localhost:3000/api/health` → 200;
   - `BASE_URL=http://localhost:3000 bash scripts/smoke.sh` → `SMOKE OK`;
   - `npm run data:check > drill-after.txt && diff drill-before.txt drill-after.txt`
     → без відмінностей (дані не втрачено);
   - `npm run ops:report -- drill-server.log --window 60` → `ALERT`
     лише у вікнах збою.

Якщо за 30 хвилин відновлення не підтверджено — ведучий сам запускає
`docker compose start db` і фіксує «зупинено ведучим».

## 4. Розбір (разом, 10–15 хвилин)

- Масштаб і пріоритет: кого зачепило, що не працювало, скільки часу.
- Чинники збою і чому його не помітили раніше (наприклад: немає
  автоматичного сповіщення — health 503 видно, лише якщо хтось дивиться;
  контейнер не перезапускається після ручної зупинки; в інтерфейсі
  немає банера «сервіс недоступний»).
- **Щонайменше дві коригувальні задачі** в Jira — власник, строк,
  спосіб перевірити ефект. **Одну виконати до захисту й перевірити
  повторним прогоном навчань.**
- Короткі рядки ретроспективи: що добре / що покращити / дія з
  власником і строком.
